# APFS Read-Write Support Roadmap

The key principle is **don't enable writes until allocation, copy-on-write metadata updates, and checkpoint publication work together as one recoverable transaction**. A bitmap bit by itself is not a safe allocator.

## Milestones and ordered tasks

| Order | Milestone | Tasks | Validation / exit criteria |
|---|---|---|---|
| **0** | **Define the initial supported scope** | Target disposable, unencrypted, single-device APFS images. Initially reject Fusion/multi-device layouts, CAB layouts the implementation does not support, sealed volumes, and other unsupported features. Keep mounts read-only by default and prohibit other writers to the test image. | Unsupported layouts fail clearly. Existing read-only mount and file-reading tests still pass. |
| **1** | **Confirm Space Manager decoding** | Boot with the current decoder and scanner in `sys/fs/apfs/apfs_subr.c`. Compare its geometry, free counts, bitmap interpretation, and candidate location with an independent APFS tool or a known-good image. Check bitmap bit order and polarity rather than assuming them. | Space Manager, CIB, chunk, bitmap, and aggregate free counts agree independently. The same polarity is observed consistently. Any mismatch is explained before continuing. |
| **2** | **Complete read-only allocation validation** | Validate relevant object types, ranges, indexes, chunk counts, and bitmap references. Identify which blocks are immediately allocatable versus reserved or delayed for reuse. Explicitly account for the internal pool, allocation zones, and free queues—or reject layouts whose allocation rules aren't implemented. | On multiple disposable images, the scanner reports only plausible candidates; no candidate is treated as safe merely because a bitmap bit looks free. Corrupt or unsupported metadata fails closed. |
| **3** | **Add an in-memory reservation model** | Implement candidate selection for the supported scope. Serialize reservations so simultaneous operations can't choose the same block. Track reservations per transaction and release them on abort. Do not write bitmap or other disk metadata yet. | Stress tests show no duplicate reservations. Injected failures release reservations. Disk images remain byte-for-byte unchanged. |
| **4** | **Build transaction and copy-on-write I/O foundations** | Define transaction state and abort behavior. Write new blocks rather than overwriting live metadata. Assign valid object IDs and transaction IDs, calculate checksums, and order writes and flushes according to APFS checkpoint rules. Keep the old checkpoint usable until the new one is safely published. | Unit and image tests verify COW writes, checksums, abort cleanup, and ordering. Simulated interruption before checkpoint publication leaves the old image mountable and unchanged as a committed state. |
| **5** | **Implement transactional Space Manager updates** | In one transaction, COW the allocation bitmap and the relevant CIB and Space Manager metadata; update chunk and device counts consistently. Implement APFS free-queue/reaper behavior before reusing released blocks. | After a test transaction and reboot, an independent checker agrees on free-space totals. Aborted or interrupted transactions do not leak blocks or mark live blocks free. |
| **6** | **Implement the metadata update core** | Implement COW B-tree insert/update/remove and OMap updates, including node splits and variable-length records. Handle root changes and checkpoint mappings required to publish new objects. | Exercise trees with empty, full, and split nodes. Reopen images with an independent checker and verify old and new tree records. Force failures at each update stage and verify recovery. |
| **7** | **Add limited filesystem write operations** | Start with the smallest useful operation: create an empty regular file, updating its inode, directory record, object IDs, volume counters, and required trees atomically. Then add small file writes and extent allocation; later handle larger writes, truncation, and sparse files. | Each operation survives sync, clean unmount, and reboot. Read the result through NetBSD and an independent APFS implementation and compare names, sizes, metadata, and file contents. |
| **8** | **Implement delayed frees and broader mutations** | Add unlink, truncation, rename, directory creation/removal, and reclamation only after their shared metadata and free-queue semantics are understood. Avoid immediate reuse of blocks that snapshots or older checkpoints can still reference. | Snapshot/checkpoint scenarios do not cause premature reuse. Repeated create/write/delete cycles preserve consistency and expected free-space accounting. |
| **9** | **Add explicit, opt-in read-write mounting** | Respect the caller's mount mode, open the device for writing only when requested, and wire up write, fsync, sync, unmount, and error paths. Keep read-only as the default until all prior milestones pass. | A read-only mount cannot write. A read-write mount is possible only for the validated supported scope. Errors never leave a success-shaped partially committed operation. |
| **10** | **Run durability and compatibility qualification** | Test workloads on disposable images with interruption at transaction boundaries, repeated remounts, near-full volumes, and concurrent operations. Document unsupported cases and recovery limits. | Independent APFS checks pass after stress and crash tests. No known data loss, duplicate allocation, or unrecoverable checkpoint state remains for the supported scope. |

## Immediate next step

The next actionable item is **Milestone 1**: collect the `apfs_spaceman` output from the test machine and compare it with an independent APFS reader. The important lines are the validated free-block total and the scanner's bitmap polarity and candidate details. That confirms—or exposes errors in—the assumptions the current read-only scanner makes.

Until Milestones 4–6 are complete and validated, keep the filesystem forced read-only. The current allocator and B-tree insertion routines are still placeholders; connecting them to the write path before those foundations exist could corrupt the volume.
