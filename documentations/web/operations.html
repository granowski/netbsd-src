Empty-file creation

Creating a nonexistent name runs lookup with create intent, then inserts an inode record and directory record in a transaction. An empty file has no data extent, so creation does not allocate a file-data block. Copy-on-write B-tree nodes, object-map metadata, the volume superblock, and allocator metadata can still require physical blocks.

lookup (ENOENT)
  -> VOP_CREATE
  -> transaction / am_lock
  -> inode + directory records (B-tree copy-on-write)
  -> reserve blocks as needed
  -> Space Manager update
  -> checkpoint map + container superblock

Writing data

apfs_vop_write() begins a transaction, finds any existing extent, reserves a new physical block, writes the block, updates the extent record and inode, then commits. A partial write copies prior block contents when an old extent exists; a hole is zero-filled before the new bytes are copied into place. Replaced data blocks are queued for freeing rather than reused in the same reservation search.

Deleting or replacing data

Removing a file's last link or truncating data removes relevant filesystem records and queues physical extents for freeing. At commit, the allocator update clears the corresponding bitmap bits and adjusts per-chunk and device free counts. Free-queue and crash-recovery behavior remains a development limitation; do not infer mature APFS guarantees from the presence of these code paths.

Directory iteration reports end-of-directory only after a complete B-tree scan. If the caller's buffer fills, iteration stops without marking EOF so the next call can continue from its cookie.

Reading a stalled operation

TraceMeaning
tx_alloc ... begin Transaction entered block reservation.
resv_alloc read CIB / read bitmap Allocator is reading the indicated metadata buffer.
resv_alloc success Reservation succeeded in memory; commit has not been proven.
spaceman_update complete Allocator metadata staging returned; checkpoint publication may still be pending.
container superblock write Checkpoint publication is in progress. Correlate by XID.

Kernel stacks and lock-owner diagnostics are necessary to establish a deadlock. A long gap between trace messages alone does not prove a lock cycle. More detail is in create/write paths and locking and stall diagnosis.
